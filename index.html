Part I

Tracing & Memory Foundations

The algorithmic principles of automatic memory management: reference counting limitations, Tri-Color abstraction proofs, JIT barriers, and sliding compaction.

01 Cycle Leakage

Reference Counting vs. Tracing: Cyclic Reference Leakage

Automatic memory management divides into two historical paradigms: Reference Counting (RC) and Tracing Garbage Collection.

In Reference Counting (used in CPython and Swift ARC), each object maintains an integer tracking the number of active references pointing to it. While RC reclaims memory eagerly when counts hit zero, it suffers from a fatal flaw: Cyclic Reference Leaks. If Object A references Object B and Object B references Object A, their reference counts remain $\ge 1$ indefinitely even if the entire graph is severed from all application GC roots! Tracing GC solves this by traversing reachable paths directly from GC roots (thread stacks, JNI registers, static classes).

02 Marking Proofs

Tri-Color Marking Invariants: White, Grey & Black

Formulated by Dijkstra and Steele, the Tri-Color Abstraction models the progress of concurrent tracing collectors by categorizing heap objects into three sets:

  • White: Unvisited candidate objects. At the end of marking, White objects are guaranteed unreachable and will be swept/reclaimed.
  • Grey: Visited objects whose outgoing field references have not yet been traversed. The GC marker's active worklist.
  • Black: Live objects whose outgoing references have all been fully scanned. Black objects contain zero pointers to White objects.

A concurrent GC is sound if and only if it preserves the Strong Tri-Color Invariant: no pointer from a Black object may directly target a White object without passing through an intermediate Grey object. If a mutator thread writes a Black-to-White pointer while deleting the Grey-to-White link, the White object would be erroneously collected—causing catastrophic memory corruption!

03 Compiler Barriers

JIT Barrier Dynamics: Post-Write Card Marking vs. Load Barriers

To preserve GC invariants without stopping application threads, JIT compilers inject tiny machine-code instructions around memory access operations:

  • Post-Write Barrier (Card Marking): Executed after reference stores. Performs a fast bitshift: card_table[addr >> 9] = 0 to mark the enclosing 512-byte card dirty for minor collections ($\approx 1\text{--}2\text{ instructions}$).
  • Pre-Write Barrier (SATB): Intercepts field overwrites during concurrent marking, logging the old pointer value into a thread-local buffer to preserve a snapshot of reachable state.
  • Load Barrier (ZGC): Intercepts object dereferences (o.field), testing colored pointer bits to relocate and self-heal forwarded references concurrently.
04 Compaction Math

Mark-Sweep vs. Mark-Compact: Sliding Compaction

Simple Mark-Sweep collectors reclaim dead objects in-place, adding free slots to an allocation free-list. Over time, alternating allocations and frees produce severe External Fragmentation: memory contains plenty of aggregate free space, but no single contiguous gap large enough to satisfy large array allocations.

Mark-Compact collectors solve fragmentation by physically sliding all surviving live objects toward one boundary of the heap, consolidating all remaining space into a single contiguous free block. This allows ultra-fast bump-pointer allocations, at the cost of updating all cross-heap pointers to relocated objects.

Part II

Generational Heaps & The JVM

How production runtimes exploit object lifespan statistics: Eden and Survivor spaces, Card Table write barriers, TLAB bump allocators, and CMS failure modes.

05 Generational GC

The Weak Generational Hypothesis: Eden, Survivor & Tenuring

Decades of empirical systems analysis across Lisp, Smalltalk, and Java confirm the Weak Generational Hypothesis: the vast majority of allocated objects die shortly after creation (infant mortality rates routinely exceed 95% within milliseconds).

The HotSpot JVM organizes the heap into generations: Young Generation (composed of Eden and two alternating Survivor spaces, S0 and S1) and Tenured (Old) Generation. New allocations enter Eden. When Eden fills, a fast Minor GC copies the few surviving objects into a Survivor space and increments their age counter. Objects that survive multiple collection rounds (exceeding -XX:MaxTenuringThreshold) are promoted into the Old Generation.

06 Cross-Gen Pointers

Card Tables & Remembered Sets (RSet): Cross-Generational References

If an Old Generation object points to a Young Generation object, a Minor GC must treat the young object as live. However, scanning the entire multi-gigabyte Old Generation to find these references would ruin the sub-10ms pause objective of Minor GC!

To eliminate full Old Gen scans, the JVM maintains a Card Table: a linear byte array where each byte corresponds to a 512-byte "card" of Old Gen memory. Whenever an application thread stores a pointer from Old Gen to Young Gen, the JIT write barrier marks the card DIRTY (0x00). During Minor GC, the collector scans *only* the dirty cards, inspecting just a fraction of a percent of Old Gen memory.

07 Allocation Speed

Thread-Local Allocation Buffers (TLAB) & Bump-the-Pointer

On modern servers with 128+ hardware threads, allocating every object directly into a shared global heap would result in catastrophic atomic CAS (Compare-And-Swap) lock contention on the heap top pointer.

The HotSpot JVM allocates each thread a private Thread-Local Allocation Buffer (TLAB) inside Eden. Allocating inside a TLAB requires only a local bump-pointer instruction: top += size; return top; with zero lock contention! Only when a thread exhausts its TLAB does it synchronize with the global heap to allocate a fresh TLAB chunk.

08 CMS Autopsy

CMS Autopsy: Floating Garbage & Concurrent Mode Failure

The Concurrent Mark Sweep (CMS) collector was the JVM's pioneering low-latency collector. However, because CMS does not compact Old Gen memory (relying on free-lists), it creates severe memory fragmentation.

Furthermore, because mutator threads run concurrently during sweeping, they create Floating Garbage that cannot be collected until the next cycle. If allocation surges outpace concurrent sweeping, or if fragmentation prevents allocating a large promoted object, CMS suffers a Concurrent Mode Failure: the JVM triggers an emergency fallback to a single-threaded Serial Mark-Compact collector, freezing production services for tens of seconds!

Part III

Low-Latency Collectors: G1GC & ZGC

How modern collectors achieve predictable tail latencies: G1GC region evacuation, ZGC colored pointers, multi-mapping virtual memory, and self-healing load barriers.

09 G1 Architecture

G1GC Region Architecture: Eden, Survivor, Old & Humongous

Introduced to replace CMS, the Garbage-First (G1) Collector breaks away from contiguous generational memory spaces. Instead, G1 partitions the entire heap into approximately 2,048 uniform Regions (ranging from 1MB to 32MB in powers of two).

Region roles are assigned dynamically: a region can be Free (F), Eden (E), Survivor (S), or Old (O). Objects that exceed 50% of a region size are classified as Humongous Objects and allocated across contiguous runs of dedicated Humongous regions.

10 G1 Evacuation

G1GC Mixed Evacuation Set & Pause Time Modeling

G1 delivers predictable latency by allowing operators to configure a soft pause time target (e.g. -XX:MaxGCPauseMillis=200). During a Mixed GC, G1 evacuates all Young regions plus a selected subset of Old regions.

G1 uses historical statistical decay models to calculate how long each region will take to evacuate. It sorts Old regions by their garbage ratio and selects the highest-yielding regions that fit within the remaining pause time budget—hence the name Garbage-First!

11 ZGC Internals

ZGC Colored Pointers & Multi-Mapping Address Space

The Z Garbage Collector (ZGC) is a scalable low-latency collector designed to handle multi-terabyte heaps with maximum pause times under 1 millisecond. ZGC achieves this by executing virtually all work concurrently with application threads, including object relocation!

To track object lifecycle state without modifying object headers, ZGC stores metadata directly in the reference pointer via Colored Pointers. A 64-bit reference allocates 44 bits for address space (up to 16TB RAM) and 4 bits for GC metadata: Finalizable, Remapped, Marked0, and Marked1. Using OS mmap() multi-mapping, the Linux page table aliases all three color bit combinations to the exact same physical memory frames!

12 Self-Healing

ZGC Self-Healing Load Barriers & Concurrent Relocation

How can ZGC move objects to new memory addresses while application threads are actively reading them? Through the Self-Healing Load Barrier.

When an application thread executes o.field, the CPU runs a small test instruction on the pointer's color bit. If the pointer has not yet been updated to the relocated address, the load barrier triggers a brief slow path: it consults ZGC's in-memory forwarding table, updates the heap reference in-place to the new location (Self-Healing!), and returns the new object. All subsequent reads by any thread execute via the single-cycle fast path!

Part IV

References, Safepoints & Latency

How runtimes prevent memory leaks and coordinate thread pauses: Soft, Weak, and Phantom references alongside JVM safepoint stall diagnostics.

13 Reference Strengths

Reference Strengths: Soft, Weak, Phantom References & Cleaners

Java defines four distinct levels of reference reachability in java.lang.ref:

  • Strong Reference: Standard variable assignments (Object o = new Object()). Prevents GC reclamation.
  • Soft Reference: Cleared by the GC only when heap memory pressure approaches OutOfMemoryError. Ideal for memory-sensitive in-memory caches.
  • Weak Reference: Cleared eagerly during the next GC cycle if no strong references exist. Used in WeakHashMap to prevent canonical mapping memory leaks.
  • Phantom Reference: Enqueued into a ReferenceQueue after the object has been finalized. Its get() always returns null to prevent object resurrection. Used by modern java.lang.ref.Cleaner to safely release off-heap native memory (e.g. Netty direct byte buffers).
14 Safepoint Latency

JVM Safepoint Mechanics & Time-To-Safepoint (TTSP) Stalls

A Stop-The-World (STW) GC pause cannot begin until all active application threads have reached a Safepoint—a point in bytecode execution where the thread's stack and register contents are known and consistent.

The time between the JVM requesting a safepoint and all threads actually stopping is called Time-To-Safepoint (TTSP). If a thread is executing an uncounted loop (e.g. for (int i=0; i<len; i++) without -XX:+UseCountedLoopSafepoints), the JIT compiler strips safepoint polling checks to optimize loop performance. The entire JVM must freeze, waiting seconds for that single thread to complete its loop before GC work can even begin!
